# Shared runner snapshots

The user explicitly chose the same architecture as Claude++: calculate on the machine holding the original logs and read a small shared snapshot over RC. The user then explicitly removed raw-log fallback from the receiving side. This supersedes directory concurrency; retain the bounded transport isolation, but remove the obsolete remote raw-log reader and its dedicated tests.

## Contract

- Use the existing local `createSessionStore` and metric formula as the authority. Snapshots live under `$CODEX_HOME/.session-stats/<thread-uuid>.json`; no chat text, source paths or credentials are included.
- Protocol v1 has exactly `schemaVersion`, `producer` (`codex-session-stats`), `threadId`, `publisherId`, `revision`, `generatedAt`, and `stats`. The projected stats are the existing numeric/boolean fields plus status. Size is at most 16 KiB, maximum age 30 seconds, future clock allowance 5 seconds. Revisions are positive safe integers and publisher IDs are UUIDs.
- The publisher checks tracked sessions every 2 seconds, publishes changed values immediately and unchanged values every 10 seconds. A bounded local filesystem scan discovers up to eight recently modified sessions every 15 seconds, including background sessions. Explicit local UI requests immediately track/publish their session; the interest cache holds at most 32 sessions. A remote session needs a producer-generated snapshot; when absent the receiver explains that it is waiting for the runner and retries.
- Write via an exclusive temporary file and atomic rename, with directory, destination ownership/type and cancellation checks. Do not write below a watched tweak installation. Preserve unknown files and remove only owned temporary files. Completed snapshots may remain after stopping; expiry prevents treating them as current. This avoids deleting a replacement published by a newer runtime during hot reload.
- Local UI responses use the successfully published sample. A failed publication returns an explicit unavailable state rather than claiming a shared sample that was never written.
- The receiver derives the snapshot location from a validated native `thread/read` rollout path. Check generated-directory/file types and symlinks, parse bounded content, validate identity/time/numbers, reject revision rollback and retired publishers, and keep caches isolated by host and thread. It may retain a previously accepted sample only within its freshness window.
- Snapshot reads use a bounded per-request transport budget (64 KiB encoded envelope, 5 seconds). The UI waits at most 750 ms per call and polls the background lookup. Missing, unavailable or expired snapshots return an explicit unavailable reason and retry; no remote original-log download or directory traversal is permitted. Invalid identity, invalid schema/numbers, future samples, replay and a fresh producer-reported source failure fail closed.
- Older never-tracked sessions use a small demand lease under `.session-stats/requests/<thread-uuid>.<request-uuid>.json`. Each renewal creates a new immutable nonce file so expiry cleanup cannot delete a newer renewal. It contains only a fixed producer/schema, thread ID and requestedAt, at most 1 KiB, renewed at most every 10 seconds. The receiver invokes an internal `snapshot/request` operation, not an invented backend RPC. Main binds the thread ID and uses a separate guarded transport capability to write only the derived marker through the existing native file API. Generic file writes remain rejected. Validate directories, existing marker ownership and identities; abort before subsequent operations on timeout/cancellation. The publisher creates the request directory and independently checks at most 256 entries every 2 seconds, so a blocked historical read cannot prevent demand discovery. Demand-only interest expires after 30 seconds; only validated expired markers may be removed.
- Hot reload waits for the previous publisher disposal before permitting a replacement publisher to start or serve local results. A shared main-process drain barrier preserves this ordering through rapid repeated reloads, preventing an old in-flight atomic rename from overwriting a new publisher's sample.

## Acceptance

Verify protocol/expiry/replay/identity/resource cases, real atomic file publication and background discovery, cold/error/retry paths without raw-log downloads or remote directory traversal, disposal, local/published/remote exact-value parity, lifecycle and UI reason messages. Run full tests and independent review. Finally install the uncommitted runtime on the already connected peer with hash guards, measure a real cold snapshot lookup and a later update, compare the exact snapshot revision on both ends, and verify normal code after diagnostic removal. Publication was excluded from the initial implementation scope; subsequent release authorization and checks are recorded in the implementation plan.
