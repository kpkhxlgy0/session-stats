# Remote continuation history parity

The user requested fixing Remote Control history reading and verifying real local/remote session-average TPS equality. Real evidence: an ordinary two-turn session agreed exactly, but a continued session's full local history had 34 turns while the remote reader saw only its latest four. A second real remote continuation requires a 53,226,738-byte historical prefix, exceeding the previous 32 MiB remote limit.

Both paths must reuse the existing local history resolver and metrics core. Introduce optional filesystem/path/source-discovery/record-validation adapters to createSessionStore, with unchanged local defaults. Remote discovery uses the native read-only fs/readDirectory API, follows only this session's rollout files, preserves archived-copy precedence, validates exact byte and ordinal history boundaries, and stops at valid fork boundaries. Missing/ambiguous/invalid histories must not return latest-segment partial totals.

The native host supports whole-file reads only. Bound downloads to 128 MiB per file and 256 MiB per history/cache, serialize heavy polls, and cache unchanged files in process memory only. Use 15-second normal polling and 60-second polling for large histories. Revalidate file metadata and identities before accepting a sample; invalidate on truncation, replacement, changed paths or disconnect. Native transport allows only thread/read, fs/getMetadata, fs/readFile and fs/readDirectory; file requests may take up to 120 seconds and the encoded response cap is 192 MiB. Do not run remote commands or alter rollout files.

An active latest file may append while the older history is being downloaded. A serialized verification read may accept that captured snapshot only if the returned content strictly extends the exact captured bytes and retains its creation identity, type and all existing ancestor/root/thread checks. Statistics are as of the captured bytes, not a promise that the file remains unchanged until the network response arrives. A later mtime change cannot invalidate an already captured prefix observation; a rewrite or truncation present in the confirmation payload still fails. The captured buffer retains its original metadata cache key so the following poll does not skip new records. Metadata-only changes without strict content extension remain errors. The confirmation uses the replacement logical-history budget rather than charging the latest file twice; the temporary confirmation buffer is not cached.

The implementation changes neither the TPS formula nor dependencies. Publication was excluded from the initial implementation scope; the user's subsequent authorization and v0.2.1 release checks are recorded in the implementation plan. Local/remote comparison is for the same captured history; in-flight generation and refresh delays can temporarily produce different snapshots. Real-session validation must use native RC reads and the production stores, with any diagnostic hooks removed afterward.
